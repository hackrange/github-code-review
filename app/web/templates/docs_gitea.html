Connecting Gitea and Forgejo

One page for both, because they are the same to set up.
Back to connections
Forgejo was forked from Gitea and still speaks the same API, so the token, the addresses and the scopes below are identical for the two of them. Pick the one you actually run in the connection: it is the name that appears on every finding and in every report, and being told you are running the other one is the kind of small wrongness that makes somebody doubt the rest of the page.

Making the token

  1. Sign in as the account that can see what you want scanned.
  2. Settings, then Applications.
  3. Under Manage access tokens, give it a name and tick these permissions, all of them read:
    read:repository, read:organization, read:user
  4. Generate it and copy it now. Neither of these shows a token twice.

Nothing needs write. The scanner only ever reads: the one write in the whole codebase is GitHub's installation token call, which has no equivalent here and is never made.

A token reaches everything its account can see rather than one organization, so one connection usually covers the whole instance. That is the opposite of a fine grained GitHub token, which is pinned to a single owner and needs one connection each.

Filling in the connection

  • Web address — your server on its own, for example https://git.example.com. Finding links are built from it.
  • API address — the same host with /api/v1 on the end, filled in for you as you type the one above.
    Opening it in a browser shows a page of API documentation or a 404, depending on the version. Either is normal: it is a prefix rather than a page. Use the Test button to check it.
  • Organization — optional. Empty scans every organization the token can see, along with the account's own repositories and anything it has been added to as a collaborator, which is usually what you want. Name one to narrow it.

Links go to /src/branch/, not /blob/

Neither of these has a /blob/ route at all, so a GitHub shaped link is a 404 rather than a redirect. Findings from this connection are written with the paths the host actually serves: /src/branch/main/app.py#L12 for a file on a branch and /src/commit/<sha>/app.py#L12 for one at the commit a credential was found in.

What is not available

Dependency alerts, code scanning, secret scanning alerts and the dependency graph are GitHub features. Neither Gitea nor Forgejo has an equivalent, so this skips them rather than calling an endpoint that is not there and reading the empty answer as good news.

Organization members, teams and pull requests do exist here, and are not wired up yet. They are spelled differently enough that the GitHub calls would come back wrong rather than empty — the member listing has no role filter, so asking it for the administrators returns everybody — and a report saying every member owns the organization is worse than a report that does not say. Who can reach each repository is still collected, with each person's real permission asked for one at a time, because the listing itself does not carry it.

What runs, which is the bulk of it: credentials across the full git history, code analysis, infrastructure as code, workflows, SBOM and dependency vulnerabilities, licenses, triage, exceptions, and both report files.
