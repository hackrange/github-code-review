AI analysis

A second reader for one finding at a time. Somebody presses Validate with AI on a finding, and the model configured here reads the finding, the code around it and the decisions already made nearby, and says whether it is as bad as its grade and why. The answer is kept on the finding with the model's name on it. A reading lower than the grade lowers it, except on a credential or a known exploited package, and a person's regrade always has the last word. What the model says covers other findings becomes a learned rule, so the same question is not paid for twice. It never changes a state or an exception.

What goes out

Every question carries the finding, the reasons behind its grade, what is recorded about the repository, and other findings nearby with the reasons people gave when they decided about them. Never the people who can reach the repository, and never the author of the commit.

The lines around a code or configuration finding, and for a vulnerable package the places in the repository that use it. Fetched from the branch at the moment of asking, not stored. This is what makes the answer worth having, and it is also your source code leaving this installation for the provider above, so it is worth checking that is somewhere your organization allows it to go. Never sent for a credential, whatever this says, because the lines around a credential contain the credential.

Only the advisory id goes to osv.dev, and it is a public identifier. The advisory's own description is usually what says which part of a package is broken.

The security report asks many small questions rather than one large one. It plans each answer to fit well inside the service's limit, thinking included, and spaces its questions out so a minute's budget is never exceeded. 0 means no per minute limit.

Auto LLM review

When a scan finishes, the findings it saw for the first time are validated the same way as pressing the button on each one, and the answer is kept on the finding under the name auto-review. A finding a learned rule already covers is answered by the rule, with no request sent. Credentials and known exploited packages are not sent, because validation may not lower them. Nothing goes out while the provider above is off.

The automatic review waits between questions so it never sends more than this in a minute, however many scans finish at once. Set it below what your provider allows, to leave room for people pressing the button and for the security report.

The worst are read first. A first scan of a large estate turns up everything as new, and this keeps it from becoming a very large bill. Whatever is over the limit can still be picked from the findings list with the AI review filter. 0 means no limit.

Code reasoning

Some weaknesses are a check that is not there: a handler that loads a record by the id it was sent without asking whether the caller may see it, or an admin action whose page hides the button but whose server never checks the role. No pattern can see those. When this is on, code picks the request handlers that read the request, touch stored data and take an id or do something privileged, and the model reads each one with the access checks it calls. Nothing else in the repository is sent. An answer is kept, so a handler nobody changed is never asked about again. It runs after each scan, on every branch that gets code scanning, and only on a branch that moved since it was last read: a branch still on the same commit is not even fetched. A connection can switch it off for its repositories. What it finds is filed for a person to confirm, and it never lowers or closes anything. It needs sending code switched on above.
