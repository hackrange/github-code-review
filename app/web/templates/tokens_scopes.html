{# What each token scope is for. Shown on the Tokens tab and the Pipeline sample code tab, so the two can never say different things. #}
ScopeWhat it is forWhat it can reachGive it to
reports Pipelines and scripts that read results: the fix plan, the deploy check, findings, SBOMs, trends, and exceptions. It can ask for an exception, change or withdraw your own, and on an administrator's account revoke exceptions and exclusions. Only repositories your account can open, and only your own exceptions unless you approve them. It can never approve one. The whole-estate report files need an administrator's account as well. A build or deploy pipeline. This is the one the sample kit uses.
review Sends code to be checked and gets the problems back, without saving anything. Used by the editor plugins. Only the code it sends. Nothing is stored and no finding is made. Your editor (VS Code, JetBrains, Eclipse).
rules Reads the triage rules and exclusions, so an editor hides the same noise this server does. The rules, and only the exclusions for repositories you can see. Your editor, alongside review.
approve Approves and rejects exceptions, and adds exclusions, such as excluding a credential's fingerprint everywhere it appears. Administrators' tokens only, checked on every call. Only findings your account can see. These take findings out of the report files, so keep this off any token a pipeline holds. An administrator's own script or triage tool.
gate Runs the pull request gate: scans only what a pull request changed and answers pass, warn or fail before it merges. The pull requests it is asked about, on repositories you can see. A pull request check in CI.

Tick only what a token needs. A pipeline that only reads results needs reports alone, so if it leaks it cannot be used to send code or run gate checks. Make one token per pipeline, so one can be revoked without breaking the others.
